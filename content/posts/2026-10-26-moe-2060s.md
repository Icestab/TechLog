手上这张 RTX 2060 SUPER 只有 8 GB 显存，主机内存 16 GB，平时跑跑 9B 级别的稠密模型绰绰有余。这次想试试更激进的：把一个 35B 的 MoE 模型（Qwen3.5-MoE，40 层、256 专家、每 token 只激活 8 个，约 3B 激活参数）用 IQ3_XXS 量化到 12.76 GiB，靠 llama.cpp 的专家卸载塞进这套硬件。结果是**生成 54 tok/s，显存 7.35 GB，16 GB 内存刚好够用**——但过程中有三个反直觉的结论，不看数据很难猜对方向。

测试环境：RTX 2060 SUPER 8 GB / i5-8500 / 16 GB DDR4 / Arch Linux / llama.cpp v0.7.0 / CUDA 13.4。

## 一、先说结论

| 场景 | 参数 | 生成 | Prefill | 显存 |
|---|---|---|---|---|
| 聊天 / 长回复 | `--cpu-moe --moe-cache-mib 5500` | **54.0 tok/s** | 426 tok/s | 7350 MiB |
| 长文档问答 | `--n-cpu-moe 20` | 38.3 tok/s | **641 tok/s** | 7750 MiB |
| 均衡 | `--n-cpu-moe 30 --moe-cache-mib 2400` | 48.7 tok/s | 514 tok/s | 7214 MiB |

三个反直觉的结论，下面逐条用数据说明：

1. **放显存的专家层越少，生成反而越快**（38.3 → 54.0 tok/s）。
2. **`--moe-cache-mib` 是这套方案的核心**，开与不开差 41%，但它和计算缓冲抢显存。
3. **Prefill 和生成速度是反向的**，选配置前先想清楚你的负载是「长输入」还是「长输出」。

## 二、为什么 35B 能在 8 GB 卡上跑

MoE 的解码开销不看总参数量，看**每 token 激活多少**。这个模型 256 个专家里只选 8 个：

```
每层专家权重 ≈ 293 MiB（IQ3_XXS，40 层共 11.5 GiB）
每 token 每层只读 8/256 → 约 9.2 MiB
```

于是权重可以整个放在内存里，每个 token 只从内存里取它真正用到的那一小部分。显存则留给注意力层、KV cache 和计算缓冲。

llama.cpp 提供三个相关参数：

| 参数 | 作用 |
|---|---|
| `--n-cpu-moe N` | 前 N 层的专家放 CPU（内存），其余放显存 |
| `--cpu-moe` | 所有专家都放 CPU，等价于 `--n-cpu-moe 40` |
| `--moe-cache-mib N` | **给留在 CPU 的专家在显存里开一个 LRU 缓存** |

第三个是关键。它的实现（`src/llama-moe-cache.cpp`）是一个逐层共享的 LRU 表：命中的专家直接用显存里的副本，不用再从内存搬。MoE 的路由是偏斜的——热门专家会被反复选中，所以缓存命中率相当可观。

注意 `--moe-cache-mib` 是**精确缓存**，不是近似量化，不影响输出质量。

## 三、实测：显存怎么分最快

固定 32k 上下文、q8_0 KV、`-ub 512`，只改专家分配和缓存大小，每组跑 3 次取中位数：

| 配置 | 显存 | 生成 tok/s | Prefill（4.9k） |
|---|---|---|---|
| `--n-cpu-moe 20`（不开缓存） | 7750 MiB | 38.3 | **641** |
| `--n-cpu-moe 24 --moe-cache-mib 800` | 7378 MiB | 39.8 | — |
| `--n-cpu-moe 26 --moe-cache-mib 1200` | 7188 MiB | 41.8 | — |
| `--n-cpu-moe 28 --moe-cache-mib 1800` | 7202 MiB | 45.7 | — |
| `--n-cpu-moe 30 --moe-cache-mib 2400` | 7214 MiB | 48.7 | 514 |
| `--n-cpu-moe 34 --moe-cache-mib 3200` | 6838 MiB | 49.8 | — |
| `--n-cpu-moe 38 --moe-cache-mib 4000` | 6462 MiB | 49.6 | — |
| `--cpu-moe --moe-cache-mib 5000` | 6850 MiB | 52.4 | — |
| **`--cpu-moe --moe-cache-mib 5500`** | 7350 MiB | **54.0** | 426 |
| `--cpu-moe --moe-cache-mib 6000` | — | **OOM** | — |

### 1. 反直觉之一：GPU 层越少越快

按直觉，放显存的层越多应该越快。实际相反。

原因是这个模型的专家**太小**：hidden 2048、专家 FFN 512。一次只算 8 个专家，每个专家的三个矩阵都很小，GPU 的 kernel 启动开销占了主导，SM 根本喂不饱。而把层腾到 CPU、把显存让给缓存之后，热门专家常驻显存，CPU 侧的内存带宽压力显著下降——**省下来的显存带来的收益，大于丢掉的那几层 GPU 算力**。

所以最优解是「全部专家放内存 + 5.5 GB 显存做缓存」，而不是「尽量往显存塞」。

### 2. 反直觉之二：缓存和计算缓冲抢显存

`--n-cpu-moe 20` 时显存已经用到 7750 MiB，只剩 442 MiB。这时加 `--moe-cache-mib 400` 直接加载失败：

```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 252.00 MiB failed: out of memory
```

缓存 6000 MiB 也是同样的死法。想开大缓存，必须先把专家层挪到 CPU 腾出空间——这就是为什么「层少 + 缓存大」能成立。

### 3. 代价：Prefill 掉 34%

缓存对预填充几乎没用。预填充是 512 token 的批处理，每个 token 激活的专家几乎不重复，缓存全 miss，所有专家都要从内存过一遍。

```
--n-cpu-moe 20  → 641 tok/s
--n-cpu-moe 30  → 514 tok/s
--cpu-moe       → 426 tok/s（慢 34%）
```

一个 32k 上下文的文档，纯预填充要 **75 秒**。所以：

- 聊天、长回复 → 选最快生成档
- 长文档问答、RAG → 选最快 prefill 档
- 两者都要 → 中间档

## 四、长上下文的真实表现

同一个模型，64k 上下文（KV 只占 10 层，q8 约 680 MiB）：

| 指标 | 值 |
|---|---|
| 显存 | 7624 MiB |
| Prefill（37.5k prompt） | 478 tok/s，耗时 79 秒 |
| 生成（37k 上下文） | 29 tok/s |
| 生成（短上下文） | 44–54 tok/s |

上下文越长生成越慢是正常的，但注意 29 tok/s 相比短上下文的 54 tok/s 掉了近一半——MoE 在长上下文下的注意力开销比同尺寸稠密模型更明显。

## 五、内存才是真正的瓶颈

模型 12.76 GiB，内存 16 GB。看起来宽裕，实际上：

```
模型页缓存    13.9 GB
系统占用       1.5 GB
```

`free` 会显示 `available` 还有 13 GB，但那是因为模型是 mmap 的、算在 buff/cache 里。**一旦有别的程序抢内存，专家权重会被踢出页缓存**，MoE 解码立刻退化成「每个 token 读一次磁盘」，速度掉到个位数。

llama.cpp 日志里也有提示：

```
tensor overrides to CPU are used with mmap enabled - consider using --load-mode none
```

`--load-mode none` 会强制全量载入内存，避免缺页，但 12.76 GiB + 系统在 16 GB 上只剩不到 2 GB 余量，很容易触发 swap。**不建议**，除非你加到 32 GB。

实际建议：跑这个模型的时候别开浏览器和 IDE。

## 六、和 9B 稠密模型的对比

同样这张卡，MiMo-V2.6-9B Q4_K_M 全量放显存：

| | 35B MoE（IQ3_XXS） | 9B 稠密（Q4_K_M） |
|---|---|---|
| 生成 | 54 tok/s | 56 tok/s |
| Prefill | 426 tok/s | **1294 tok/s** |
| 显存 | 7350 MiB | 7368 MiB |
| 上下文 | 64k | **96k** |
| 内存占用 | 14 GB 页缓存 | ~0 |

**生成速度基本打平，prefill 只有三分之一。** 这是 MoE 卸载的典型特征：解码时每个 token 只读少量专家，内存带宽够用；预填充时所有 token 一起算，CPU 侧成为瓶颈。

所以这套方案适合「一问一答慢慢聊」，不适合「灌一篇长文档再问」。

## 七、质量：别忽略量化损失

12.76 GiB 的 35B 意味着平均 **3.06 bit/参数**。这个量化档位在量化作者的验证口径里属于「显存更紧」档：

| 档位 | 体积 | 宏平均 KL | Same-top |
|---|---|---|---|
| MINI | 10.94 GiB | 0.1992 | 83.18% |
| COMPACT | 12.76 GiB | 0.1358 | 86.15% |
| BALANCED | 13.80 GiB | 0.0959 | 88.83% |
| QUALITY | 17.50 GiB | 0.0464 | 92.26% |

16 GB 内存最多只能上到 BALANCED（13.80 GiB），QUALITY 需要 32 GB。也就是说**参数量优势被量化损失部分抵消了**——我实测这档 35B 在常识问答上和 9B Q4 打平，只在时间/日期推理上明显更强。

想真正吃到 35B 的红利，得加内存或换卡。

## 八、功耗

用墙上功率计实测（2060 SUPER，175 W 功耗墙）：

| 状态 | 显卡 | 整机 |
|---|---|---|
| 空载 | 12.3 W | 50 W |
| 满载生成 | 172 W（97% 利用率） | **240 W** |
| 预填充 | 166 W（99% 利用率） | ~230 W |

注意负载结束后显卡会在 P2 状态（1470 MHz）停留 12–15 秒，这段时间仍有约 50 W。频繁的短请求会拉高平均功耗。

CPU 侧功耗没测到（`intel-rapl` 需要 root），但 MoE 卸载会让 CPU 在生成时持续工作，整机功耗比纯 GPU 推理更高。

## 九、复现命令

下面的权重文件名是 occamy 改写版——它和同尺寸的很多衍生模型一样，都是基于 Qwen3.5-MoE 二次训练的，所以文件名和开头写的型号对不上是正常的，直接换成你手上的 Qwen3.5-MoE 35B GGUF 也能用同一套参数。

```bash
# 聊天 / 长回复（最快生成）
llama-server \
  -m occamy-1.0-abliterated-FIT-COMPACT-13G-IQ3_XXS.gguf \
  -ngl 99 --cpu-moe --moe-cache-mib 5500 \
  -c 65536 -fa on -ctk q8_0 -ctv q8_0 -ub 512 -np 1 \
  --host 0.0.0.0 --port 8080 --jinja

# 长文档问答（最快 prefill）
llama-server -m ... -ngl 99 --n-cpu-moe 20 -c 32768 -fa on -ctk q8_0 -ctv q8_0

# 均衡
llama-server -m ... -ngl 99 --n-cpu-moe 30 --moe-cache-mib 2400 -c 65536 -fa on -ctk q8_0 -ctv q8_0
```

调参顺序建议：

1. 先定上下文，算出 KV 占用（这个架构只有 1/4 的层吃 KV，很便宜）。
2. 从 `--cpu-moe` 开始，逐步给 `--moe-cache-mib` 加，直到显存剩 400–600 MiB（留给 prefill 的计算缓冲）。
3. 如果 prefill 太慢，再把专家层往显存挪（减小 `--n-cpu-moe`），同时减小缓存。

## 十、踩坑清单

1. **缓存不能超过空闲显存**：留 400–600 MiB 给计算缓冲，否则加载或 prefill 时 OOM。
2. **mmap 依赖页缓存**：内存紧张时速度会断崖式下跌，且不会报错。
3. **`-ub 512` 是 prefill 的关键**：调小能省显存，但 prefill 更慢。
4. **量化档位要看清 KL**：同样是「35B」，IQ3 和 Q4 的实际能力差距可能比 9B 和 35B 的差距还大。
5. **别用 `--load-mode none`**，除非内存 ≥ 32 GB。

## 十一、这套方案适合谁

✅ **适合**：显存 8–12 GB、内存 16 GB 以上、想在本机跑 30B 级 MoE 做日常对话、代码助手、离线实验。

❌ **不适合**：需要高吞吐 prefill 的长文档 RAG、需要跑 benchmark 刷分的场景、内存只有 16 GB 还同时开一堆程序的人。

一句话总结：**MoE 让「参数规模」和「硬件门槛」解耦了，但解耦的代价转移到了 prefill 和内存带宽上。** 知道这个代价在哪，才能把配置调对。
