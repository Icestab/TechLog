上一篇讲的是怎么在账单和日志对不上时找到真凶，这次做另一件事：**把配置改成适合个人用户的形态**——摊开成本、逐条关掉不适配的默认行为、落成可复制可回滚的清单，并说清哪些开关**故意没关**。

## 一、先说清一个会反复踩的数字

前情：2026-10-09，这套自建记忆服务的云 API 免费额度（各模型 100 万 token）在 26 分钟里被烧穿。账单上**嵌入模型 593 次调用、重排模型 100 多次调用**，而服务端日志只数到 **19 次**重排，候选合计 1092 个。

**593 是嵌入的调用数，不是重排的**——上一篇就栽在这，一路归因连刷新次数都算错。重排真实量级是 100 多次（15 次内部刷新 × 8 + 用户侧 19 ≈ 139），对日志 19 次约 **7 倍**、不是 30 倍。完整排查见站内《免费额度 26 分钟被烧穿：一次「日志骗人」的成本排查》。

## 二、归因：按 token 分列，别按调用次数

Hindsight 自带 LLM 调用记账，直接查：

```
GET /v1/default/banks/<bank>/llm-requests?limit=&offset=
GET /v1/default/banks/<bank>/llm-requests/stats?period=7d&trunc=day
```

两个坑：列表键是 `items` 不是 `requests`；**按 `operation` 分组、别按 `scope`**——`scope` 把心智模型刷新记成 `reflect`，按它分组只能得出"reflect 很贵"这种没法行动的结论。

优化前那 24 小时的构成（窗口含了后面要讲的一次性清扫）：

| operation | 调用 | 未命中输入 | 缓存命中 | 输出 | 思考 | 估算成本 | 占比 |
|---|---:|---:|---:|---:|---:|---:|---:|
| **consolidation** | 192 | 1,634,512 | 637,056 | 247,143 | **434,931** | ¥3.0114 | **74.1%** |
| refresh_mental_model | 155 | 574,818 | 1,680,512 | 63,486 | 0 | ¥0.7354 | 18.1% |
| mental_model_delta_ops | 24 | 149,137 | 66,112 | 27,944 | 0 | ¥0.2063 | 5.1% |
| retain | 31 | 34,619 | 107,776 | 30,327 | 6,869 | ¥0.1112 | 2.7% |
| **合计** | 402 | | | | | **¥4.0643** | |

金额按列表价估算：未命中输入 1.0、命中 0.02、输出与思考 2.0 元/百万 token。

两个可立刻行动的信号：**consolidation 吃掉四分之三**，它才是主战场、不是让日志骗人的重排；**思考 token 独立且很贵**（按 output 计价），consolidation 的 434,931 思考 ≈ ¥0.87，占全库 21%、它自身的 29%。反过来看 refresh 那行——155 次只花 ¥0.7354，因为思考是 0、74.5% 的输入命中缓存（命中价便宜 50 倍）：同一张表里"关思考"和"提高命中"两个杠杆的效果一目了然。

## 三、真正的放大器是一条链

一次 consolidation 不是一次调用，是**平均 3 次、最多 22 次** LLM 调用的多轮循环，单次 ¥0.14 ~ ¥0.35。它被谁触发？读代码：

```python
# memory_engine.py —— retain 的副作用
if config.enable_observations and config.enable_auto_consolidation:
    await self.submit_async_consolidation(...)           # 每次 retain 都提交一次整合
await self.submit_async_graph_maintenance(...)           # 不花 LLM 钱
await self._submit_vector_index_maintenance_quietly(...) # 不花 LLM 钱
```

整合完成又触发心智模型刷新，链条变成：

```
每次 retain
   └─→ 一次 consolidation（多轮 LLM，含思考）
          └─→ 每个心智模型一次全量重刷（reflect 工具循环）
```

**这条链没有任何内置节流**（`DEFAULT_ENABLE_AUTO_CONSOLIDATION = True`），实测一天跑十几次整合。

根因一句话：**默认配置是给"有预算的多用户系统"设计的**——每个数据变化都触发一次全量再加工，每次再加工内部又是多轮 LLM 循环，而个人的数据变化频率远高于他的预算能承受的再加工频率。

三个独立放大器，每个都能单独关：

| # | 放大器 | 机制 | 代价 |
|---|---|---|---|
| 1 | 每次 retain 触发一次整合，整合又触发每个模型全量重刷 | 无内置节流 | 整合占成本 74% |
| 2 | 每次召回把最多 300 个候选送交叉编码器重排 | 单次约 3.06 万 token | 26 分钟烧穿免费额度 |
| 3 | 思考 token 按 output 计费 | 占整合成本 29%；且造成读超时误判 | 钱 + 长尾延迟 + 任务失败 |

## 四、四个杠杆

**杠杆 1：关掉重排（bank 级，立刻见效还更快）**

```
curl -X PATCH http://<host>:8888/v1/default/banks/hermes/config \
  -H "Authorization: Bearer <key>" -H 'Content-Type: application/json' \
  -d '{"updates": {"enable_reranking": false}}'
```

这个开关**只把 `cross_encoder` 降级成 `rrf`**，是引擎里唯一一处判断。而 consolidation 的内部召回显式传了 `reranking="interleave"`，走融合不算 API，所以关掉重排**不影响整合的去重质量**——这一点我是怀疑过、实测才排除的。

**它是 bank 级的**——"设了 RRF 怎么还有重排调用"通常就是另一个库没关：hermes 关掉后 535ms、重排 API +0，另一个库还开着时 3437ms、+1 次，补关后 435ms、0 次，白拿 8 倍提速。附带的坑：**新建 bank 默认 `enable_reranking=true`**，再加一个库立刻开始打重排。

**杠杆 2：关掉自动整合，改成按时触发**

```
curl -X PATCH http://<host>:8888/v1/default/banks/hermes/config \
  -H "Authorization: Bearer <key>" -H 'Content-Type: application/json' \
  -d '{"updates": {"enable_auto_consolidation": false}}'
```

关掉后停掉所有自动提交路径（代码里 4 处守卫）与每 5 分钟的维护例程，但**不影响手动触发**。**`enable_observations` 必须保持 `true`**：整合编排器第一行就是 `if not config.enable_observations: return {"status": "disabled"}`，两个都关的话手动触发也静默返回 disabled，看着像"整合不工作"，其实是自己把源头关了。

连带收益：刷新的主力触发路径就是"整合完成后"——整合从一天十几次降到 1 次，刷新跟着变 1 次。

**杠杆 3：只关刷新/反思路径的思考，保留整合的**

```yaml
HINDSIGHT_API_MENTAL_MODEL_REFRESH_LLM_REASONING_EFFORT: "none"
HINDSIGHT_API_REFLECT_LLM_REASONING_EFFORT: "none"
# 故意不设 HINDSIGHT_API_CONSOLIDATION_LLM_REASONING_EFFORT
```

这是分层判断，不是一律关：**刷新走的是 reflect 工具循环**（多轮慢慢查），思考只加钱不加质量，还会因为"思考期间不产出可见字节"触发读超时 → 重试 → 撞墙钟；**整合和 retain 没有工具循环兜底**，是知识质量的源头，思考在这里真在干活，关掉等于省小钱毁内容。

关掉后原先为绕超时调大的 600/300 **可退回官方默认的 300/120**。

**杠杆 4：6 小时刷新节流**

```
HINDSIGHT_API_MENTAL_MODEL_MIN_REFRESH_INTERVAL_SECONDS: "21600"
```

默认值是 **0**，完全没节流。但这个参数极易误解：它是**下限/刹车，不是调度/发动机**——`_defer_refresh_within_min_interval` 只在"已有人提交一次刷新"后判断够不够 6 小时，不够就把这次扣住（`DeferOperation` → `next_retry_at`，无重试计数无错误），它**从不产生**刷新，只对自动刷新生效，手动刷新随时立即执行。

实证（这一条我一开始也说反了）：北京 11:14、11:30、11:40 **连续三次整合而刷新 0 次**（触发到了、闸门关着），直到 15:05 才出现下一次；整合侧 19:02 → 次日 04:03 **近 9 小时零整合**，而同期刷新间隔在 1.5h、4.5h、5.5h 和几分钟之间乱跳，**没有任何固定周期**——若 6 小时是调度，这些间隔该是等距的 6 小时。

## 五、验证：哪些是硬的

**硬证据四条**：重排归零（两库对照 + 服务端 `[rrf-passthrough]` vs `[cross-encoder]` 日志 + 3437ms→435ms，三重独立）；自动触发切断（隔离 A/B/C 实验 + 改动后 6 次 retain 零整合）；6 小时确实在刹（北京 11:14、11:30、11:40 三次整合连续零刷新，直到 15:05 才出现下一次；整合侧 19:02→次日 04:03 零整合）；定时任务跑通（04:03:46 整合 → 04:05:11 刷新，17 次整合里唯一落在凌晨的就是它）。关思考消除了超时：`mental_model_delta_ops` 此前**连续 4 次**撞墙钟，关后思考记为零、单次 1.5–27 秒，当前窗口 155 条刷新全 success。

**没法验证的：优化前后的金额对比。** `llm_requests` 默认只留 24 小时，等优化做完，优化前的基线已被滚掉，现在拿到的窗口横跨优化前后、不是干净对照。所以只能报告**结构性变化是确定的**（触发链切断、重排归零、刷新压到一天一次，覆盖 74% + 18% = 92% 的成本量），**不能给"省了 X%"的承诺**——整合一天一次后每次要处理的记忆更集中、单次更贵，按量计费那部分省得不按比例。

## 六、两个必须知道的坑

**① 最该记的一条：`llm_requests` 只留 24 小时，会吃掉你的基线。**

```yaml
DEFAULT_LLM_TRACE_RETENTION_DAYS = 1        # 默认只留 1 天
DEFAULT_RETENTION_SWEEP_INTERVAL_SECONDS = 3600   # 每小时清一次
```

它存完整 prompt 原文（单行平均 30 kB），所以默认留得短，但调大代价可忽略：440 行才 13 MB、30 天预计 200–400 MB（可用空间的 0.3%）。**动手前先调大**（`HINDSIGHT_API_LLM_TRACE_RETENTION_DAYS: "30"`），它找不回已丢的基线、只让你从现在攒得住。这类优化的通用建议：**第一天先存基线**。

**② 关掉自动整合引入了单点故障。**

替代它的是 **agent 侧每日定时任务**：每天 **04:00（北京）**、no-agent 纯脚本（跑脚本零 token）、结果与失败都投递回会话。`observation` **只由整合产出**，心智模型和知识页**只读 observation**。定时要是挂了（key 过期、容器重建、脚本报错）：retain 照常入库、事实继续涨，你不会觉得有问题，但下游内容冻在原地、`is_stale` 也不亮（它比的是 observation 层）。观测方法：隔几天看 `total_observations` 涨没涨，不涨就是链路断了，**建议加失败通知**。`pending_consolidation` 一整天持续增长是正常的，别误判成积压故障。

另外切换开关只停掉未来的自动触发、**不消化已积压的记忆**：首次触发会撞上大积压，按单轮上限 100 条自己排队，实测 7 轮约 75 分钟、¥1.20——一次性成本，别当成"优化没效果"。

## 七、可迁移的结论

**按资源量归因，不按调用次数。** 同一账单里"590 次 × 29 token"和"120 次 × 30,570 token"单价几乎相同，**单次消耗却差约 1050 倍**（30,570 vs 29），只看次数会把大头看漏。归因表要同时列未命中输入、缓存命中、输出、**思考**四列——思考常被忘掉，而它按 output 计价。

**找"放大器"，不找"贵的那一次"。** 真正的省法不是把某次调用调便宜，而是问"每次什么都会触发一串贵调用"——这次收益最大的动作就是把 `retain → 整合 → 每个模型全量重刷` 这条链从源头切断。

**分层思维：按"有没有兜底"决定关不关**——有工具循环兜底的路径该关思考，没有兜底、决定内容质量的路径该留。

**谁该怎么做：**

- **个人自用、每天几十次写入** → 重排关、自动整合关、改一天一次定时、刷新节流 6 小时、只关刷新与反思的思考——这就是本文的配置清单。
- **多用户或团队共享、写入稀疏** → 自动整合可以留着，它保证 observation 始终新鲜；重排按召回精度决定，嫌贵先压 `HINDSIGHT_API_RERANKER_MAX_CANDIDATES` 而不是直接关。
- **所有人都该做的** → 先把 `LLM_TRACE_RETENTION_DAYS` 调大，做不做优化都成立。

**考虑过但没执行**（供参考，非"已做"）：整合的思考降档而非关（`CONSOLIDATION_LLM_REASONING_EFFORT=low`，省那 29%）、服务级钉死新建 bank 默认值（`HINDSIGHT_API_DEFAULT_BANK_TEMPLATE`，对已有库无效）、给整合换更便宜的模型。三项都**没试**。

**回滚都很快**：重排与自动整合是 bank 级 override，改回 `true` 或删掉那条覆盖即可；思考与节流是 env，`docker compose up -d` 约 60 秒，无 schema 变更、无数据迁移。

稳态金额还在观察，拿到干净的前后对照再补，而补的前提是先调大记账期——**实测保留仍是 24 小时**（最早一条记录距现在 24.6 小时，`HINDSIGHT_API_LLM_TRACE_RETENTION_DAYS` 还没生效），不改它，下一轮对照的基线同样会被滚掉。
