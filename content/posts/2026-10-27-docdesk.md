折腾了好几天本地模型部署，最开始的原意是给 Hindsight 配个本地推理。今天终于有正式用途了，先把结论放前面：**本地部署当省钱工具是不成立的**——折算硬件成本和电费，跑起来并不比云端便宜多少。想来想去只剩一个理由：隐私。而隐私这件事，前阵子刚让我栽过一个跟头。

## 一、省钱这条理由，先划掉

我一直在想本地部署到底好在哪。省钱吗？并不会。显卡是钱、16 GB 内存是钱、满载整机 240 W 也是钱，摊下来不比按 token 计费的云端服务便宜多少。把「省钱」从动机里划掉之后，剩下的答案就只有一个，而且很老套：**数据不出本地**。

## 二、那次保险条款的翻车：涂抹 ≠ 遮挡

前段时候本来想让 Hermes 研究一下保险条款，我以为把 PDF 上的个人信息涂抹后就行了，结果那层遮挡并不会真正掩盖信息——底层内容照样能被读出来，后面擦屁股费了很大力气。

其实这已经不是第一次了。之前很多次为了分析个人隐私文件，都得先手工裁剪掉敏感页、敏感段，又麻烦又容易漏。文件只要出过一次本机，就说不清它还去过哪；而裁剪、涂抹这些补救，本质上都是在赌「遮得住」。这次翻车让我明白，与其赌遮挡，不如让文件根本出不了门。

## 三、docdesk：用后即焚的本地文档问答台

于是有了自己的本地项目：**docdesk**（https://github.com/Icestab/docdesk.git）。一句话概括——拖 PDF/扫描件进去，用本地大模型问它，关掉就什么都不剩：不联网、不落盘、不留日志。

数据流只有三层，全部在本机：

```
浏览器（本机或局域网）
      │  上传 / SSE 流式回答
      ▼
app.py   ← 文档文本、BM25 索引、对话历史，只存在进程堆内存里
      │  OpenAI 兼容 /v1
      ▼
llama-server（只监听本机回环地址，日志输出直接丢弃）
```

启动就两个命令，停掉即销毁：

```bash
cd ~/docdesk
./docdesk.sh                 # 只监听本机回环，SSH -L 转发访问，最稳
./docdesk.sh --lan           # 监听局域网，打印带一次性令牌的地址
./docdesk.sh stop            # 从别的终端停掉
```

支持 PDF（含扫描件 OCR）、docx、xlsx、图片、表格类文本；超过 4.2 万 token 自动切检索模式，答案里的 `[3]` 这类编号点一下就跳回原文页码。模型被要求：数字、日期、金额、条款号照抄原文，资料里没有就说「资料中未提及」——合同问答最怕它顺嘴编。

## 四、凭什么敢说「关掉就没了」

这是整个项目最花心思的部分，每一处数据都对得上「怎么消失」：

| 数据 | 在哪 | 怎么消失 |
|---|---|---|
| 上传的文件、抽出的文字、检索索引、对话历史 | Python 进程堆内存 | 进程退出即归还内核，关机断电清空 |
| 界面里的聊天记录 | 浏览器内存（无 localStorage / IndexedDB / Service Worker） | 刷新即丢、关标签页即丢 |
| llama-server 的日志 | `/dev/null` | 从未写过 |
| 崩溃转储 | 启动脚本里 `ulimit -c 0` | 不会生成 |
| 临时文件 | 没有；`/tmp` 本身也是 tmpfs | — |

刻意没做的事：不缓存磁盘、不写 sqlite、不导出 PDF、不做「历史会话」。

## 五、实测：带标记的文档，全盘零命中

嘴上说不落盘不算数，得搜。用一个带唯一标记的文档走完「上传 → 提问（让模型把标记念出来）→ 页面销毁」，然后全盘搜：

```bash
grep -aRl "标记串" /tmp /dev/shm "$HOME" <系统日志目录> <coredump目录> 2>/dev/null
journalctl --since "-40 min" | grep -c "标记串"
```

2026-10-27 实测结果：**文件 0 命中，journal 0 命中**，退出后显存回到 9 MiB、服务端口全部关闭。README 里还留了一条「顺手清别处」的提醒：这工具自己不落盘，但以前的崩溃转储、别的聊天前端可能替你记过同一批文档。

## 六、35B 够不够用：两个任务，两种答案

最初的设想里，9B 模型通不过 Hindsight 的评测，35B 的 occamy 也不太行——那条路没走通。但换成合同文档问答，**实测 35B 已经可以非常精准地总结分析合同文档**，我这台 8 GB 显存 + 16 GB 内存的机器跑它就是上限（配置和实测数据见上一篇[《8 GB 显存 + 16 GB 内存跑 35B MoE》](/posts/2026-10-26-moe-2060s/)：生成 54 tok/s）。同一个模型，一边「不太行」、一边「非常精准」，差别在于任务要的不是刷榜分数，而是把条款、日期、金额从你自己的文档里原样捞出来。

性能上限跟着硬件走：**如果你机器更强，可以用更大的模型**，docdesk 本来就只是个壳，`models.conf` 里换路径即可。README 里记的能力边界——跨几十页的金额求和、扫描件形近字、长文档逐页比对会漏——那是 **9B 模型**的真实水平；换到 35B 之后，这些实测已经没有了。

## 七、取舍：谁该本地，谁该留云端

- **该本地**：手里有 8 GB 以上显存的卡、经常要碰合同/病历/流水这类不想出门的文件——一台机器、一个命令，用后即焚。
- **该云端**：硬件不够、或者只是偶尔用——为偶尔一次去买卡不划算，云端 + 仔细脱敏仍然可行，只是要做好「遮挡可能遮不住」的心理准备。
- **两者都要**：像我这样日常跑云端、敏感件临时起本地的，docdesk 就是那个「临时」的落点。

一句话：本地部署买不到便宜，买到的是**文件从头到尾没离开过这台机器**的确定性。
